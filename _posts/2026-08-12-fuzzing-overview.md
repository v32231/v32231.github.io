다음 학기 캡스톤에서 퍼징 관련 프로젝트에 합류할 예정이라 퍼징에 대해서 좀 더 알아봐야겠다고 생각해서 이 포스트를 올리게 되었다. 퍼징은 입문 자체는 쉬운데 좀만 깊게 들어가면 너무 어려운 것 같다. 퍼징 잘 쓰시는 분들 존경합니다..

기본적으로 용어나 어느 정도의 개념은 ’The Art, Science, and Engineering of Fuzzing: A Survey’라는 논문과 Google에서 공개한 퍼징 관련 깃허브 자료를 참고했다. 해당 논문은 초록에서 현대 퍼저의 성능을 뒷받침하는 관련 문헌과 퍼징의 실무(art), 과학(science), 공학(engineering) 분야의 다양한 발전을 체계적으로 검토하고, 모델 퍼저의 각 단계에서 이루어지는 설계 결정들을 탐구한다고 설명한다.

# 용어

## 퍼징(Fuzzing)

퍼징은 프로그램에 다양한 입력(문법적·의미적으로 비정상적인 입력 포함)을 반복적으로 제공하고 실행하여 오류나 취약점을 찾는 소프트웨어 테스트 기법이다.

## 퍼저(Fuzzer)

퍼저는 퍼징을 수행하거나 지원하는 도구로, 테스트 입력을 생성·변형하고 PUT를 실행하거나 그 실행 결과를 평가하는 역할을 수행한다. 구체적인 역할 범위는 퍼저에 따라 다를 수 있다.

## 테스트 대상 프로그램(PUT, Program Under Test)

PUT는 테스트 대상 프로그램을 의미한다. 본 포스트에서는 퍼징 대상 프로그램을 PUT로 부르겠다.

## 퍼즈 테스팅(Fuzz testing)

퍼즈 테스팅은 PUT가 정확성 정책을 위반하는지 확인하기 위해 테스트하는 것을 의미한다.

## 퍼즈 캠페인(Fuzz campaign)

퍼즈 캠페인은 특정 정확성 정책을 기준으로 PUT에 퍼저를 실행하는 것을 의미한다.

## 버그 오라클(Bug oracle)

버그 오라클은 PUT의 실행 결과가 정의된 정확성 정책을 위반했는지를 판단하는 메커니즘으로, 퍼저의 일부로 구현될 수도 있다.

## 퍼즈 알고리즘(Fuzz algorithm)

퍼즈 알고리즘은 퍼저가 테스트 입력을 생성·선택·변형하는 방식을 결정하는 알고리즘이다.

## 퍼즈 구성(Fuzz configuration)

퍼즈 구성은 퍼즈 알고리즘의 동작을 제어하는 매개변수와 그 값들의 집합을 의미한다.

## 시드(Seed)

시드는 테스트 케이스를 생성하기 위한 초기 입력 또는 기존 입력으로, 퍼저가 이를 변형하여 새로운 테스트 케이스를 생성하는 데 사용한다. 퍼즈 구성에 포함될 수 있다.

## 시드 풀(Seed pool)

시드 풀은 퍼저가 유지·관리하는 시드들의 집합이다. 퍼저에 따라 퍼징 과정에서 유망한 입력이 추가되거나 제거되며 동적으로 갱신될 수 있다.

## 코퍼스(Corpus)

코퍼스는 퍼징에 사용되는 테스트 입력들의 집합이다. 초기 입력으로 제공되는 시드 코퍼스와 퍼징 과정에서 새롭게 발견되어 추가되는 입력들을 포함할 수 있다. 현대적인 커버리지 가이드 퍼저에서는 시드 풀과 유사한 의미로 사용되는 경우가 많다.

## 퍼즈 반복(Fuzz iteration)

퍼즈 반복은 알고리즘 루프(논문에서 제시된 범용 테스트 알고리즘, Algorithm 1)를 한 번 실행하는 것을 의미한다.

## 퍼즈 실행(Fuzz run)

퍼즈 실행은 입력 평가(INPUTEVAL) 단계에서 하나의 테스트 케이스를 사용하여 PUT를 한 번 실행하는 과정을 의미한다.

## 오버헤드(Overhead)

오버헤드는 작업을 수행하는 과정에서 추가적으로 발생하는 실행 시간, 메모리, CPU 등의 자원 소모를 의미한다. (예시: 계측 삽입, 메모리 스냅샷 복원, SMT 솔버(SMT solver) 호출 등)

## 커버리지(Coverage)

커버리지는 PUT 실행 시 어떤 코드가 실행되었는지 측정하는 지표이다.

- **라인 커버리지(Line coverage)**: 전체 코드 줄 중 실제 실행된 코드 줄의 비율이다.
- **블록/노드 커버리지(Block/Node coverage)**: 프로그램의 기본 블록(Basic block) 중 몇 개가 실행되었는지 측정한다.
- **분기/엣지 커버리지(Branch/Edge coverage)**: 제어 흐름 그래프(Control-Flow Graph, CFG)에서 기본 블록 사이의 분기 또는 제어 흐름 엣지 중 실제로 실행된 항목을 측정한다. (예를 들어, `if` 문의 참 경로와 거짓 경로를 모두 실행했는지 확인한다.)

퍼징에서는 보통 블록 또는 분기(엣지) 커버리지를 실행 피드백으로 활용한다. (예시: AFL, AFL++, libFuzzer, honggfuzz)

# 개념

## 퍼즈 타깃(Fuzz target)

퍼즈 타깃은 퍼저가 생성한 입력을 받아 테스트하려는 API나 기능으로 전달하는 함수 또는 진입점을 의미한다. PUT 전체를 직접 실행하는 대신 특정 기능만 선택하여 반복 테스트할 수 있도록 하네스(Harness)의 역할을 수행할 수 있다.

대표적으로 libFuzzer에서는 다음과 같은 형태의 퍼즈 타깃을 사용한다.

```c
LLVMFuzzerTestOneInput(const uint8_t *Data, size_t Size)
```

퍼저는 다양한 입력을 위 함수에 반복적으로 전달하고, 퍼즈 타깃은 전달받은 데이터를 이용하여 실제 테스트 대상 API를 호출한다.

### 좋은 퍼즈 타깃의 조건

퍼징은 동일한 타깃을 매우 많은 횟수로 반복 실행하는 방식이므로 퍼즈 타깃의 설계가 퍼징 효율에 큰 영향을 준다.

- **다양한 입력을 처리할 수 있어야 한다.**
  - 빈 입력, 매우 큰 입력, 손상된 입력 등 예상하지 못한 데이터가 들어오더라도 퍼즈 타깃 자체가 불필요하게 종료되지 않아야 한다.
- **결정적(Deterministic)으로 동작하는 것이 좋다.**
  - 같은 입력에는 가능한 한 같은 실행 결과가 나와야 한다.
  - 입력과 관계없는 난수나 외부 상태에 의존하면 실행 피드백이 흔들려 퍼징 효율이 낮아질 수 있다.
- **실행 속도가 빨라야 한다.**
  - 불필요한 로그 출력, 파일 입출력, 반복적인 초기화와 같이 매 실행마다 큰 비용이 발생하는 작업은 줄이는 것이 좋다.
- **전역 상태(Global state)의 영향을 최소화하는 것이 좋다.**
  - 이전 실행에서 변경된 상태가 다음 입력의 실행 결과에 영향을 주면 비결정적 동작이 발생할 수 있다.
- **테스트 범위를 너무 넓게 잡지 않는 것이 좋다.**
  - 하나의 거대한 API 전체를 한 번에 퍼징하기보다 기능이나 입력 형식별로 여러 퍼즈 타깃으로 나누면 탐색 공간을 줄일 수 있다.
- **초기화가 필요한 경우 가능한 한 반복 밖에서 한 번만 수행한다.**
  - 매 입력마다 동일한 초기화를 다시 수행하면 퍼즈 실행 속도가 크게 감소할 수 있다.

## 퍼즈 가능성(Fuzzability)

퍼즈 가능성(Fuzzability)은 퍼저가 입력을 생성·변형하면서 PUT의 다양한 실행 경로나 상태를 얼마나 쉽게 탐색할 수 있는지를 나타내는 개념이다.

높은 커버리지를 제공하는 좋은 시드가 있다고 해서 반드시 퍼즈 가능성이 높은 것은 아니다. 예를 들어 암호화되거나 체크섬으로 보호되는 입력은 정상적인 시드를 사용하면 깊은 코드까지 실행할 수 있지만, 단순한 바이트 변형만으로도 입력이 즉시 무효화되어 프로그램의 초기 검사 단계에서 거부될 수 있다.

### 커버리지 발견 가능성(Coverage discoverability)

커버리지 발견 가능성은 퍼저가 기존 시드에 의존하지 않고 입력을 생성·변형하여 새로운 코드 영역을 스스로 발견할 수 있는 정도를 의미한다.

즉, **현재 시드가 높은 커버리지를 갖는 것과 퍼저가 해당 커버리지를 스스로 발견하기 쉬운 것은 서로 다른 문제**이다.

커버리지 발견 가능성이 낮은 경우 다음과 같은 방법을 고려할 수 있다.

- 퍼즈 타깃의 범위를 더 작게 분리
- 사전(Dictionary)을 이용해 의미 있는 토큰 제공
- 구조 인식 퍼징(Structure-aware fuzzing) 사용
- 입력 검증이나 초기 파싱 단계가 탐색을 지나치게 막고 있는지 확인

## 구조 인식 퍼징(Structure-aware fuzzing)

구조 인식 퍼징은 입력 형식의 문법이나 내부 구조를 고려하여 테스트 케이스를 변형하거나 생성하는 방식이다.

일반적인 변형 기반 퍼저는 입력의 비트나 바이트를 직접 변형한다. 그러나 압축 데이터, 체크섬이 포함된 파일, 직렬화 형식, 프로그래밍 언어와 같이 구조가 복잡한 입력은 단순한 변형만으로 쉽게 손상될 수 있다. 이 경우 생성된 입력 대부분이 파싱 초기 단계에서 거부되어 깊은 실행 경로를 탐색하기 어려워질 수 있다.

구조 인식 퍼징에서는 입력을 다음과 같은 형태로 처리할 수 있다.

**입력 파싱 → 구조화된 내부 표현 변형 → 다시 직렬화 → PUT 실행**

libFuzzer에서는 사용자 정의 변형기(Custom mutator)를 구현하여 이러한 방식을 적용할 수 있다. 예를 들어 압축 데이터를 직접 변형하는 대신 먼저 압축을 해제한 데이터를 변형한 뒤 다시 압축하거나, PNG와 같은 파일을 구조 단위로 파싱한 뒤 필드를 변형하고 다시 정상적인 파일 형식으로 직렬화할 수 있다.

구조 인식 퍼징은 다음과 같은 입력에 특히 유용할 수 있다.

- 압축 형식
- 체크섬으로 보호된 파일 형식
- 이미지·미디어 컨테이너
- Protocol Buffers와 같은 직렬화 형식
- SQL과 같은 쿼리 언어
- 프로그래밍 언어

## 퍼징 입력 분할(Input splitting)

하나의 퍼즈 타깃이 여러 개의 인자를 필요로 하는 경우에는 퍼저가 생성한 하나의 바이트 배열을 여러 하위 입력(Sub-input)으로 나누어 사용할 수 있다.

예를 들어 정규 표현식 라이브러리를 테스트하려면 하나의 실행에서 정규 표현식, 검색 대상 문자열, 옵션 값이 동시에 필요할 수 있다. 이 경우 하나의 퍼징 입력에서 각각의 값을 결정적으로 추출하여 API에 전달할 수 있다.

입력을 분할하는 대표적인 방법은 다음과 같다.

- 입력의 처음 또는 마지막 일부 바이트를 옵션 값으로 사용
- 매직 구분자(Magic separator)를 이용해 여러 입력으로 분리
- 기존 데이터 형식의 별도 필드나 주석 영역에 부가 입력 삽입
- Protobuf와 같은 직렬화 형식 사용
- `FuzzedDataProvider`와 같은 도구를 이용하여 정수, 불리언, 바이트 배열 등을 입력에서 추출

공통적으로 사용되는 파일이나 네트워크 형식을 퍼징하는 경우에는 가능하면 기존 데이터 형식을 그대로 유지하는 것이 좋다. 그래야 기존 샘플을 시드로 활용하기 쉽고, 생성된 코퍼스를 다른 퍼즈 타깃에서도 재사용하기 쉽다.

## 코퍼스 교차 활용(Cross-pollination)

코퍼스 교차 활용은 한 퍼즈 타깃에서 생성된 코퍼스를 다른 퍼즈 타깃의 코퍼스를 확장하는 데 사용하는 방법이다.

예를 들어 서로 다른 두 라이브러리가 동일한 이미지 파일 형식을 처리한다면, 한 라이브러리의 퍼징 과정에서 발견된 유용한 입력을 다른 라이브러리의 시드로 사용할 수 있다.

동일하거나 호환되는 입력 형식을 사용하는 여러 퍼즈 타깃 사이에서 코퍼스를 공유하면 한 타깃에서 발견한 다양한 입력 구조를 다른 타깃의 탐색에도 활용할 수 있다.

# 퍼저의 분류 체계

## 블랙박스 퍼저(Black-box fuzzer)

블랙박스 퍼저는 PUT를 하나의 블랙박스로 간주하여, 프로그램 내부의 코드나 실행 경로를 분석하지 않고 입력과 출력만을 기반으로 테스트 케이스를 생성하고 동작을 평가하는 퍼저이다. (예시: zzuf, Peach의 일부 모드)

전통적인 소프트웨어 테스팅에서는 이러한 방식을 입출력 기반 테스팅(I/O-driven testing) 또는 데이터 기반 테스팅(Data-driven testing)이라고도 부른다.

## 화이트박스 퍼저(White-box fuzzer)

화이트박스 퍼저는 PUT의 내부를 분석하고, 프로그램의 내부 정보와 실행 정보를 활용하여 테스트 케이스를 생성하고 동작을 평가하는 퍼저이다. 보통 동적 심볼릭 실행을 사용하여 새로운 실행 경로를 탐색한다. (예시: SAGE, KLEE)

화이트박스 퍼징은 PUT의 상태 공간을 체계적으로 탐색할 수 있지만, 동적 계측과 SMT 솔버 등을 사용하므로 블랙박스 퍼징보다 오버헤드가 크다.

## 그레이박스 퍼저(Grey-box fuzzer)

그레이박스 퍼저는 블랙박스와 화이트박스의 중간 접근 방식으로, PUT의 전체 의미를 분석하지 않고 코드 커버리지와 같은 경량의 실행 정보를 활용하여 테스트 케이스를 생성하고 동작을 평가하는 퍼저이다. (예시: AFL, AFL++, libFuzzer, honggfuzz)

근사적이고 불완전한 정보를 사용하여 분석 오버헤드를 줄이고, 더 많은 입력을 빠르게 테스트한다.

특히 코드 커버리지를 실행 피드백으로 사용하여 새로운 코드 영역을 탐색한 입력을 시드 풀에 보존하고 다시 변형하는 방식을 커버리지 가이드 퍼징(Coverage-guided fuzzing)이라고 하며, 현대적인 그레이박스 퍼저에서 널리 사용된다.

# 퍼즈 테스팅 알고리즘

## 1. 전처리(Preprocess)

전처리 단계는 퍼즈 캠페인 시작 전, 메인 퍼징 루프를 수행할 수 있도록 준비하는 단계이다.

### 수행 작업

- **계측(Instrumentation)**: 프로그램에 추가 코드를 삽입하여 실행 중 커버리지, 메모리 접근, 시스템 호출 등 다양한 실행 정보를 수집하는 기법이다.
  - **정적 계측(Static instrumentation)**: PUT 실행 전에 소스 코드나 중간 표현, 바이너리 등에 계측 코드를 삽입한다. 일반적으로 동적 계측보다 런타임 오버헤드가 낮다.
  - **동적 계측(Dynamic instrumentation)**: 프로그램 실행 중 계측을 적용하므로 소스 수정이나 재컴파일이 어려운 대상에도 적용할 수 있지만, 일반적으로 정적 계측보다 오버헤드가 크다.
  - **실행 피드백(Execution feedback)**: 커버리지 등 실행 정보를 수집하여 그레이박스 퍼저의 입력 생성 및 시드 관리에 활용한다.
  - **스레드 스케줄링(Thread scheduling)**: 비결정적 실행을 제어하여 경쟁 조건(Race condition)과 같은 버그를 유도한다.
  - **인메모리 퍼징(In-memory fuzzing)**: 매 퍼즈 반복마다 PUT 프로세스를 새로 생성하지 않고 메모리 상태를 복원하거나 동일한 프로세스에서 테스트 대상 루틴을 반복 실행하여 초기화 오버헤드를 줄이는 기법이다.
- **시드 선택(Seed selection)**: Minset 기법 등을 이용하여 커버리지를 최대한 유지하면서 최소한의 시드 집합을 선택한다.
  - **Minset 기법**: 현재 커버리지를 유지하는 한에서 가장 적은 개수의 시드만 남기는 절차이다.
- **시드 정리(Seed trimming)**: 시드 크기를 줄여 메모리 사용량을 줄이고, 처리량을 높인다.
- **드라이버(Driver) 또는 하네스(Harness) 준비**: 라이브러리·커널 등 직접 퍼징하기 어려운 PUT를 호출하기 위한 테스트 프로그램을 작성한다.
- **모델 준비(Model construction)**: 모델 기반 퍼저의 경우 입력 형식이나 프로토콜 모델을 미리 정의하거나 학습한다.

  <span class="info-box__label">NOTE</span>
  <p class="info-box__title">실행 피드백 VS 커버리지</p>
  <dl class="info-box__terms">
    <dt>실행 피드백</dt>
    <dd>PUT 실행 후 수집되는 모든 정보</dd>
    <dt>커버리지</dt>

</aside>


<aside class="info-box">
  <span class="info-box__label">NOTE</span>
  <p class="info-box__title">비결정적 실행(non-deterministic program behavior)</p>
  <p>같은 입력을 같은 프로그램에 여러 번 넣어도 매번 실행 경로·출력·실행 시간 등이 달라지는 상태</p>
  <p class="info-box__footnote">경쟁 조건은 비결정적 실행 상황에서 대표적으로 발생할 수 있는 문제라고 보면 된다.</p>
</aside>


## 2. 스케줄링(Schedule)

스케줄링 단계는 현재 퍼즈 구성 집합, 경과 시간, 제한 시간 등을 고려해서 다음 퍼즈 반복에서 사용할 퍼즈 구성을 선택하는 단계이다.

### 스케줄링 기법

- **FCS(Fuzz Configuration Scheduling) 문제**: 제한된 시간 안에 어떤 퍼즈 구성을 선택해야 가장 많은 버그나 새로운 실행 경로를 발견할 수 있는가를 결정하는 문제이다.
  - 목적
    - 더 많은 버그 발견
    - 더 높은 커버리지 확보
  - 핵심 과제
    - **탐색(Exploration)**: 새로운 퍼즈 구성을 시도
    - **활용(Exploitation)**: 성능이 좋은 퍼즈 구성을 계속 사용
    - 모든 스케줄링 알고리즘은 탐색과 활용 사이의 균형을 맞추는 것을 목표로 한다.
- **블랙박스 스케줄링(Black-box scheduling)**
  - 충돌 발생 확률과 실행 속도를 기반으로 퍼즈 구성을 선택한다.
  - 대표 기법
    - **베르누이 시행(Bernoulli trial) 기반 모델**: 충돌 발생 확률을 추정하여 퍼즈 구성을 선택한다.
    - **MAB(Multi-armed bandit) 기반 스케줄링**: 실행 시간이 짧고, 성공 확률이 높은 구성을 우선한다.
- **그레이박스 스케줄링(Grey-box scheduling)**
  - 진화 알고리즘(Evolutionary algorithm, EA)을 기반으로 퍼즈 구성을 선택한다.
  - 대표 기법
    - **AFL**: 선호 시드(Favored seed)를 우선 선택한다
    - **AFLFast**: 희귀 경로를 우선 탐색하며 파워 스케줄(Power schedule)을 사용한다
    - **AFLGo**: 특정 코드 위치를 목표로 하는 지향성 퍼징(Directed fuzzing)
    - **Hawkeye**: 정적 분석 기반 지향성 퍼징
    - **FairFuzz**: 희귀 분기 중심 퍼징
    - **QTEP**: 결함 가능성이 높은 영역을 우선 탐색

<aside class="info-box">
  <span class="info-box__label">NOTE</span>
  <p class="info-box__title">적합도 함수(Fitness function)</p>
  <p>퍼즈 구성(주로 시드)의 우선순위를 결정하기 위한 평가 기준이다.</p>
  <dl class="info-box__terms">
    <dt>AFL</dt>
    <dd><strong>선호 시드 선정:</strong> 각 제어 흐름 엣지(Control-flow edge)를 대표하는 시드 가운데 실행 속도와 파일 크기 등을 고려해 상대적으로 효율적인 시드를 선호 시드로 선정한다.</dd>
    <dd><strong>퍼징 에너지 할당:</strong> 실행 속도, 커버리지 크기 등 여러 요소를 고려하여 퍼즈 구성에 할당할 퍼징 에너지를 조절한다.</dd>
    <dt>AFLFast</dt>
    <dd>AFL의 스케줄링 전략을 개선하여 희귀 경로 탐색을 강화한 퍼저이다.</dd>
    <dd><strong>희귀 경로 우선:</strong> 희귀한 실행 경로를 탐색하는 퍼즈 구성에 더 높은 우선순위를 부여한다.</dd>
    <dd><strong>파워 스케줄:</strong> 경로의 탐색 빈도와 선택 이력 등을 고려해 퍼즈 구성마다 퍼징 에너지를 동적으로 조절하고, 희귀한 경로를 실행하는 구성에 상대적으로 더 많은 에너지를 배분한다.</dd>
  </dl>
</aside>


## 3. 입력 생성(Input generation, INPUTGEN)

입력 생성 단계는 퍼즈 구성을 기반으로 테스트 케이스를 생성하는 단계이다.

### 입력 생성 방식

- **모델 기반/생성 기반 퍼저(Model-based/Generation-based fuzzer)**: 입력 모델을 이용하여 테스트 케이스를 생성한다.
  - 사전 정의된 모델(Predefined model)
    - 사용자가 제공하거나 퍼저에 내장된 모델을 이용한다.
    - 예시: Peach, PROTOS, Tavor, jsfunfuzz
  - 추론된 모델(Inferred model)
    - 실행 로그, 시드, 샘플 등을 분석하여 입력 모델을 자동으로 학습한다.
    - 예시: Skyfire, PULSAR, GLADE
  - 인코더 모델(Encoder model)
    - 인코더 프로그램을 이용하여 약간 비정상적인 입력을 생성한다.
    - 예시: MutaGen
- **모델 없는/변형 기반 퍼저(Model-less/Mutation-based fuzzer)**: 기존 시드를 변형하여 테스트 케이스를 생성한다.
  - 예시: 비트 플립(Bit-flipping), 산술 변형, 블록 기반 변형, 사전 기반 변형
- **화이트박스 퍼저**: 프로그램 분석을 이용하여 테스트 케이스 생성을 유도한다.
  - 동적 심볼릭 실행(Dynamic symbolic execution, DSE)
    - SMT 솔버를 이용해 경로 제약을 해결하고 새로운 입력을 생성한다.
  - 유도 퍼징(Guided fuzzing)
    - 정적·동적 프로그램 분석 결과를 이용하여 입력 생성을 유도한다.
  - PUT 변형(PUT mutation)
    - 체크섬 검사나 조건 분기를 우회하기 위해 PUT를 수정한다.

## 4. 입력 평가(Input evaluation, INPUTEVAL)

입력 평가 단계는 생성된 테스트 케이스를 이용해 PUT를 실행하고, 버그 오라클을 통해 정책 위반 여부를 판단하는 단계이다.

### 입력 평가 방식

- **버그 오라클**: PUT 실행이 정확성 정책을 위반했는지 판단하는 기준이다.
  - 충돌 기반(Crash-based)
    - 세그멘테이션 폴트(Segmentation fault) 등 치명적인 예외나 신호를 이용해 버그를 탐지한다.
  - 새니타이저(Sanitizer) 기반
    - 메모리·타입 안전성(예시: ASan, SoftBound/CETS, MEDS, TypeSan)
    - 미정의 동작(예시: MSan, UBSan)
    - 동시성 오류(예시: TSan)
  - 차등 테스팅(Differential testing)
    - 프로그램의 서로 다른 구현이나 버전의 실행 결과를 비교하여 버그를 탐지한다.
- **실행 최적화(Execution optimization)**: 반복 실행의 오버헤드를 줄여 퍼징 성능을 향상시키는 기법이다.
  - 예시: 포크 서버(Fork server), 인메모리 퍼징
- **트리아지(Triage)**: 발견된 버그를 분석하고 관리하는 과정이다.
  - **중복 제거(Deduplication)**: 동일한 원인의 버그를 하나의 그룹으로 묶는다. (예시: 스택 백트레이스 해싱(Stack backtrace hashing), 커버리지 기반 중복 제거(Coverage-based deduplication), 의미 기반 중복 제거(Semantic-aware deduplication))
  - **우선순위 평가(Prioritization)**: 버그의 심각도와 고유성을 기준으로 우선순위를 결정한다.
  - **테스트 케이스 최소화(Test case minimization)**: 버그 재현에 필요한 최소한의 입력만 남기도록 테스트 케이스를 축소한다.

  <span class="info-box__label">NOTE</span>
  <p class="info-box__title">AddressSanitizer(ASan)</p>
  <p>프로그램 실행 중 발생하는 다양한 메모리 오류를 탐지하는 새니타이저 기반 버그 오라클이다.</p>
  <dl class="info-box__terms">
    <dt>탐지 원리</dt>
    <dd>섀도 메모리(Shadow memory)를 이용하여 메모리 접근 전에 해당 주소가 유효한지 검사한다.</dd>
    <dt>탐지 가능한 오류</dt>
    <dd><strong>공간적 오류(Spatial errors):</strong> 버퍼 오버플로우, 언더플로우 등 객체의 경계를 벗어난 메모리 접근</dd>
    <dd><strong>시간적 오류(Temporal errors):</strong> UAF 등 해제된 메모리에 접근하는 오류</dd>
    <dt>장점</dt>
    <dd>프로그램이 즉시 비정상 종료되지 않는 메모리 오류도 탐지할 수 있다.</dd>
    <dt>성능</dt>
    <dd>컴파일 시 프로그램을 계측하며, 평균 약 73%의 실행 오버헤드가 발생한다.</dd>
    <dd>다른 메모리 오류 탐지 도구보다 오버헤드가 낮아 퍼징과 함께 널리 사용된다.</dd>
  </dl>
</aside>


<aside class="info-box">
  <span class="info-box__label">NOTE</span>
  <p class="info-box__title">인메모리 퍼징 VS 포크 서버</p>
  <p>PUT를 반복 실행할 때 발생하는 초기화 및 프로세스 생성 오버헤드를 줄이기 위한 실행 최적화 기법이다.</p>
  <dl class="info-box__terms">
    <dt>인메모리 퍼징</dt>
    <dd>PUT를 매번 새로 실행하지 않고 메모리 스냅샷을 복원하거나, 동일한 프로세스에서 테스트 대상 루틴을 반복 실행한다.</dd>
    <dd>반복적인 프로세스 생성과 초기화 비용을 줄일 수 있어 초기화 비용이 큰 PUT에 특히 효과적이다.</dd>
    <dd>동일 프로세스에서 루틴을 반복 호출하는 방식에서는 이전 실행의 상태나 부작용이 다음 테스트에 영향을 주지 않도록 관리해야 한다.</dd>
    <dt>포크 서버</dt>
    <dd>한 번 초기화된 부모 프로세스를 유지하고, 각 테스트마다 <code>fork()</code>로 자식 프로세스를 생성하여 실행한다.</dd>
    <dd>각 테스트가 별도의 프로세스에서 실행되어 상태 격리가 쉽다.</dd>
    <dd><code>fork()</code>가 효율적인 유닉스 계열(Unix-like) 환경에서 범용적으로 사용하기 좋다.</dd>
    <dd>대표적으로 AFL 계열 퍼저에서 사용된다.</dd>
  </dl>
</aside>


## 5. 구성 업데이트(Configuration updating, CONFUPDATE)

구성 업데이트 단계는 현재 퍼즈 반복에서 수집된 실행 결과와 퍼즈 구성을 바탕으로 퍼즈 구성 집합을 수정하는 단계이다.

### 시드 및 시드 풀 관리 방식

- **진화적 시드 풀 업데이트(Evolutionary seed pool update)**: 새로운 노드나 브랜치를 발견하는 등 적합도 기준에서 유망한 테스트 케이스를 새로운 퍼즈 구성으로 추가한다.
- **Minset 유지(Maintaining a Minset)**: 동일하거나 유사한 커버리지를 유지하면서 필요한 퍼즈 구성의 수를 줄여, 구성 집합이 지나치게 커지는 것을 방지한다.

## 6. 계속 여부 결정(Continue)

계속 여부 결정 단계는 현재 퍼즈 구성 집합을 바탕으로 새로운 퍼즈 반복을 수행할지 결정하는 단계이다.

### 조건

- `Continue` 함수에 퍼즈 구성 집합을 인자로 넣으면 `True` 또는 `False`를 반환한다.
  - True: 다음 퍼즈 반복을 수행한다.
  - False: 퍼즈 캠페인을 종료한다.
  - 단순히 시간 제한이나 반복 횟수에 의존하지 않고, 퍼저의 내부 상태를 이용해 종료 여부를 판단할 수 있다.
  - 특히 탐색 가능한 경로나 상태를 체계적으로 관리하는 화이트박스 퍼저를 모델링하는 데 유용하다.
    - 더 이상 탐색할 새로운 경로나 상태가 없다면 `False` 를 반환하여 퍼즈 캠페인을 종료할 수 있다.

# 퍼저 종류와 차이점

퍼저는 입력 생성, 실행 피드백, 스케줄링, 계측 및 실행 방식 등에 따라 동작 방식과 특징이 달라진다.

## AFL++

AFL++는 AFL(American Fuzzy Lop)을 확장한 커버리지 가이드 그레이박스 퍼저이다. PUT를 계측하여 실행 중 발생하는 제어 흐름 정보를 수집하고, 이를 피드백으로 이용해 새로운 실행 상태를 탐색한다.

### 계측 방식

AFL++는 `afl-cc`를 중심으로 여러 컴파일러 및 계측 방식을 지원한다. 일반적인 소스 코드 기반 퍼징에서는 컴파일 시 PUT를 계측하며, 바이너리만 존재하는 경우를 위한 QEMU 기반 등의 실행 방식도 제공한다.

기본적인 커버리지 피드백은 엣지 커버리지를 기반으로 한다. PUT 실행에서 새로운 엣지가 발견되거나 기존 엣지의 실행 횟수에 의미 있는 변화가 발생하면 해당 입력을 유망한 입력으로 판단할 수 있다.

### 스케줄링 기법

AFL++는 모든 시드에 동일한 퍼징 시간을 할당하지 않고 파워 스케줄을 이용하여 각 시드에 얼마나 많은 퍼징 에너지를 할당할지 결정한다.

현재 여러 파워 스케줄을 제공하며 `explore`가 기본값이다. 각 시드의 유망성에 따라 변형에 사용하는 시간을 다르게 배분한다.

또한 코퍼스(Corpus)에서 커버리지와 실행 비용 등을 고려하여 선호 시드를 선정하고 이후 퍼징에서 우선적으로 처리한다.

### 입력 생성 방식

기존 입력을 변형하는 변형 기반 방식을 중심으로 동작한다.

- 입력 변형 방식
  - 비트 플립
  - 정수 덧셈 및 뺄셈
  - 특수 정수값(Interesting integer) 삽입
  - 바이트 삽입 및 삭제
  - 여러 변형을 조합하는 Havoc
  - 서로 다른 테스트 케이스를 결합하는 Splicing
  - 사전을 이용한 토큰 삽입

AFL++는 결정적 변형과 Havoc 등 여러 변형 단계를 사용한다. Splicing은 현재 버전에서 기본적으로 비활성화되어 있으며, 필요하거나 일정 조건을 만족할 때 사용할 수 있다.

### 입력 평가 방식

계측을 통해 수집한 엣지 커버리지를 이용하여 테스트 케이스가 기존에 발견하지 못했던 동작을 발생시켰는지 판단한다.

새로운 엣지 등을 발견한 입력은 이후 다시 변형하기 위해 큐(Queue)에 보존하며, 새로운 실행 동작을 발생시키지 않은 입력은 일반적으로 보존하지 않는다.

충돌과 멈춤(Hang)도 별도로 관리하며, 커버리지 정보를 이용한 충돌 중복 제거 기능도 제공한다.

### 시드 풀 관리 방식

퍼징 과정에서 새로운 실행 동작을 발생시킨 입력을 큐에 추가하여 이후 변형의 기반으로 다시 사용한다.

큐가 증가하면 AFL++는 모든 입력을 동일하게 취급하지 않고 커버리지와 실행 비용 등을 이용하여 상대적으로 가치가 높은 선호 시드를 선택한다. 별도의 `afl-cmin`을 이용하여 현재 커버리지를 유지하면서 코퍼스 자체를 최소화할 수도 있다.

### 실행 최적화 방식

대표적인 특징 중 하나는 포크 서버이다.

PUT를 테스트 케이스마다 처음부터 `execve()`하지 않고 초기화된 프로세스를 기반으로 자식 프로세스를 생성하여 실행 비용을 줄인다.

추가적으로 하나의 프로세스에서 여러 테스트 케이스를 처리하는 지속 실행 모드(Persistent mode)와 초기화 작업 이후에 포크 서버를 시작하는 지연 포크 서버(Deferred forkserver) 등을 지원한다.

## libFuzzer

libFuzzer는 LLVM에서 제공하는 프로세스 내(In-process) 커버리지 가이드 진화적 퍼징 엔진이다. PUT와 퍼저를 하나의 실행 파일로 링크하고 특정 퍼즈 타깃(Fuzz target) 함수를 반복적으로 호출하면서 입력을 테스트한다.

### 계측 방식

기본적으로 Clang의 `-fsanitize=fuzzer` 옵션을 이용해 필요한 계측 코드와 libFuzzer를 함께 빌드하는 방식을 사용한다.

커버리지 정보는 LLVM의 SanitizerCoverage를 통해 수집하며 ASan, UBSan 등의 새니타이저와 함께 사용하는 것도 지원한다.

### 스케줄링 기법

libFuzzer는 코퍼스의 입력을 기반으로 변형을 반복하는 진화적 방식으로 동작하며, 공식 문서의 실행 예시에서는 엔트로피 파워 스케줄(Entropic power schedule)을 사용하는 것을 확인할 수 있다.

### 입력 생성 방식

기존 코퍼스의 입력을 기반으로 변형 기반 방식으로 새로운 테스트 케이스를 생성한다.

- 입력 변형 방식
  - 비트 변경
  - 바이트 변경
  - 바이트 삽입 및 삭제
  - 입력 일부 복사
  - 서로 다른 입력을 결합하는 교차(CrossOver)

사용자가 사전을 제공하여 특정 문자열이나 매직 값(Magic value) 등을 변형에 사용할 수 있다.

### 입력 평가 방식

PUT 실행에서 얻은 커버리지 등의 실행 특징(Feature)을 바탕으로 테스트 케이스가 새로운 정보를 제공하는지 판단한다.

새로운 커버리지를 발생시킨 입력은 코퍼스에 저장되며 이후 새로운 변형을 생성하는 기반으로 다시 사용된다.

ASan, UBSan, MSan 등의 새니타이저와 함께 사용할 수 있으며 충돌, 타임아웃(Timeout), 메모리 부족(OOM) 등의 실패 입력을 별도의 아티팩트(Artifact)로 저장할 수 있다.

### 시드 풀 관리 방식

새로운 커버리지를 발생시킨 입력을 코퍼스에 추가한다.

- `merge=1` 기능을 이용하면 여러 코퍼스 가운데 새로운 커버리지를 제공하는 입력만 선별하여 합칠 수 있어 커버리지를 유지하면서 코퍼스를 줄이는 데 사용할 수 있다. 또한 동일한 특징(Feature)을 유지하면서 더 작은 입력을 발견하면 기존 입력을 축소하는 기능도 제공한다.

### 실행 최적화 방식

libFuzzer의 가장 큰 특징은 프로세스 내 퍼징이다.

PUT를 별도의 프로세스로 반복 실행하지 않고 동일한 프로세스 내부에서 퍼즈 타깃 함수를 계속 호출한다. 따라서 프로세스 생성 비용을 줄일 수 있지만, 이전 실행의 전역 상태 등이 다음 테스트에 영향을 주지 않도록 퍼즈 타깃을 작성해야 한다.

일반적인 퍼즈 타깃은 다음과 같은 진입점(Entry point)을 구현한다.

```c
LLVMFuzzerTestOneInput(const uint8_t *Data, size_t Size)
```

libFuzzer가 생성한 입력이 위 함수로 반복 전달된다.

## honggfuzz

honggfuzz는 커버리지 피드백을 사용하는 진화적 퍼저(Evolutionary fuzzer)로, 소프트웨어 및 하드웨어 기반 커버리지 피드백을 지원하는 것이 특징이다.

### 계측 방식

컴파일 시점 계측(Compile-time instrumentation)을 기본 모드로 사용하며, 이외에도 환경에 따라 여러 커버리지 및 실행 피드백 수집 방식을 지원한다.

- 커버리지 및 실행 피드백 수집 방식
  - 컴파일 시점 소프트웨어 계측
  - Intel Processor Trace(PT)
  - Intel BTS(Branch Trace Store)
  - 명령어/분기 카운터
  - QEMU 모드

소스 코드를 계측하는 방식뿐만 아니라 일부 바이너리 전용(Binary-only) 환경에서도 사용할 수 있다.

### 스케줄링 기법

커버리지 피드백을 이용하여 새로운 입력을 진화시키는 진화적 방식을 사용한다.

다만 AFL++의 파워 스케줄처럼 세부적인 시드 스케줄링 정책에 대한 설명은 공식 사용자 문서에서 자세히 설명하고 있지 않다.

### 입력 생성 방식

기존 입력을 변형하여 새로운 입력을 만드는 변형 기반 진화적 퍼징을 지원한다.

커버리지 피드백과 결합하여 새로운 프로그램 영역을 발견하는 변형을 이후 퍼징에 활용한다.

### 입력 평가 방식

소프트웨어 계측이나 하드웨어 기능에서 얻은 코드 커버리지를 실행 피드백으로 사용할 수 있다.

또한 `ptrace()`와 시그널(Signal) 등의 운영체제 기능을 이용하여 충돌을 감지한다.

### 시드 풀 관리 방식

커버리지 기반 모드에서는 새로운 커버리지를 제공하는 입력으로 코퍼스를 확장할 수 있으며, 초기 코퍼스 없이 퍼징을 시작하는 것도 지원한다.

- `M` 옵션을 사용하면 커버리지를 기준으로 코퍼스 최소화(Corpus minimization)도 수행할 수 있다.

### 실행 최적화 방식

일반적인 별도 프로세스 실행뿐만 아니라 지속 실행 퍼징(Persistent fuzzing)을 지원한다.

지속 실행 모드에서는 PUT의 API를 동일한 프로세스에서 반복 호출할 수 있어 프로세스 초기화 비용을 크게 줄일 수 있다.

또한 다중 프로세스(Multi-process) 및 다중 스레드(Multi-thread) 기반 실행을 지원한다.

## Radamsa

Radamsa는 정상적인 샘플 입력을 읽어 이를 변형하여 비정상적인 테스트 케이스를 만들어내는 변형 기반 테스트 케이스 생성기(Test case generator)이다.

AFL++, libFuzzer, honggfuzz와 달리 커버리지 피드백을 중심으로 PUT의 실행 결과에 따라 시드 풀을 진화시키는 구조가 핵심이 아니다. 입력 샘플을 받아 다양한 형태로 변형된 데이터를 생성하는 데 초점이 맞춰져 있다.

### 계측 방식

PUT의 코드 커버리지를 측정하기 위한 계측을 기본적으로 요구하지 않는다.

따라서 PUT를 직접 계측하거나 소스 코드를 수정하지 않고도 생성된 테스트 데이터를 프로그램에 전달하여 사용할 수 있다.

### 스케줄링 기법

AFL++와 같은 커버리지 기반 시드 스케줄링을 사용하지 않는다.

PUT에서 얻은 커버리지 피드백을 이용해 특정 시드를 우선적으로 선택하는 방식보다는, 제공된 샘플 데이터를 기반으로 새로운 테스트 입력을 생성하는 방식에 초점을 맞춘다.

### 입력 생성 방식

기존 샘플을 바탕으로 다양한 변형을 적용하여 비정상적인 입력을 생성한다.

‘샘플 → 변형 → 퍼징된 테스트 케이스’ 형태로 볼 수 있다.

### 입력 평가 방식

Radamsa 자체의 핵심 역할은 테스트 케이스 생성이다.

따라서 AFL++처럼 PUT의 커버리지를 직접 추적하고 그 결과를 기반으로 다음 변형 방향을 결정하는 피드백 루프를 기본으로 하지 않는다. 생성된 데이터를 PUT에 전달하고 충돌 등의 결과를 관찰하는 부분은 사용 환경과 함께 구성할 수 있다.

### 시드 풀 관리 방식

커버리지 피드백을 이용해 새로운 입력을 자동으로 시드 풀에 추가하고 진화시키는 구조가 핵심 기능은 아니다.

사용자가 제공한 샘플들을 변형의 기반으로 사용한다.

## Jackalope

Jackalope는 Google Project Zero에서 공개한 커스터마이징 가능한 분산형 커버리지 가이드 바이너리 퍼저(Coverage-guided binary fuzzer)이다. 특히 소스 코드가 없는 블랙박스 바이너리 퍼징을 주요 대상으로 하며 Windows, macOS, Linux, Android를 지원한다.

### 계측 방식

Jackalope는 기본적으로 TinyInst를 이용한 동적 바이너리 계측을 사용하여 소스 코드가 없는 바이너리에서도 커버리지를 수집할 수 있다.

Linux에서는 소스 코드가 존재하는 경우 SanitizerCoverage를 사용하는 방식도 지원한다.

### 스케줄링 기법

Jackalope는 퍼징할 샘플을 우선순위가 있는 큐로 관리한다.

기본 정책에서는 한 샘플을 변형한 실행이 새로운 커버리지를 만들어내지 못하면 해당 샘플의 우선순위를 낮추고, 새로운 커버리지를 발견하면 우선순위를 다시 높인다. 이를 통해 새로운 실행 영역을 발견하는 데 도움이 되는 샘플을 상대적으로 더 많이 퍼징한다.

또한 하나의 샘플을 선택한 뒤 일정 횟수 동안 반복적으로 변형하고 실행한 후 다음 샘플로 이동하는 구조를 사용한다.

### 입력 생성 방식

기본적으로 바이너리 형식에 사용할 수 있는 일반적인 변형기를 제공하며, 문법 기반 변형 엔진(Grammar-based mutation engine)도 포함한다.

사용자가 직접 사용자 정의 변형기(Custom mutator)를 구현하여 대상 프로그램이나 파일 형식에 특화된 변형 전략을 적용할 수도 있다.

추가적으로 사전(Dictionary)을 이용한 변형과 결정적·비결정적 변형을 지원한다.

### 입력 평가 방식

TinyInst 등의 계측을 통해 얻은 커버리지를 이용하여 새로운 실행 영역을 발견한 입력을 판단한다.

새로운 커버리지는 재실행을 통해 재현 여부를 확인할 수 있으며, 안정적으로 재현되지 않는 커버리지는 불안정한 커버리지(Flaky coverage)로 취급하여 해당 정보만 제공하는 샘플은 저장하지 않는다.

충돌 역시 여러 번 재실행하여 재현 여부를 확인할 수 있으며, 재현되지 않는 충돌은 불안정한 충돌(Flaky crash)로 구분한다.

### 시드 풀 관리 방식

초기 입력 디렉터리의 샘플을 기반으로 코퍼스를 구성하고, 새로운 커버리지를 제공하는 입력을 코퍼스에 추가한다.

새로운 샘플을 저장하기 전에 크기를 최소화하는 기능을 기본적으로 사용할 수 있으며, 커버리지 정보를 기준으로 입력 코퍼스를 정리하는 데에도 활용할 수 있다.

### 실행 최적화 방식

파일 또는 공유 메모리(Shared memory)를 이용하여 샘플을 PUT에 전달할 수 있다. 공유 메모리를 사용하면 매 입력마다 파일을 작성하는 비용을 줄일 수 있다.

TinyInst의 지속 실행 모드를 이용하면 하나의 프로세스에서 특정 타깃 함수를 반복 실행하여 프로세스 초기화 비용을 줄일 수 있다.

또한 여러 퍼징 스레드를 이용한 단일 머신 병렬 실행과 서버/워커 구조를 이용한 여러 머신의 분산 퍼징을 지원한다. 서버는 워커에서 발견한 샘플, 충돌, 커버리지 정보를 수집하고 다시 다른 워커에 배포할 수 있다.
